# Demo dataset — 25 October 2026

The existing local `RadiologyCenter` development database has been populated with synthetic training records. Names, notes and business references use `DEMO`; email addresses use reserved `example.invalid`. No real patient information was imported. The original administrator and password/account state were preserved and verified by a before/after fingerprint.

A new COPY_ONLY backup was created and verified with SQL Server checksum before any insertion. Its exact server-side path is recorded in `audit-results/demo-data-2026-10-25/manifest.json`. This is a recovery artifact; restoring it later would discard changes made after that backup.

## Using the records

Start the application from Visual Studio against its existing development settings and sign in with the existing administrator. Refresh a page if it was open before seeding.

1. In Calendar, inspect the four equipment rows in day view and switch to week/list; open an appointment's details. Use an empty interval and a DEMO patient to practice booking.
2. In Visits, compare the different states and balances. One scheduled visit has a partial payment; a clinical visit remains unpaid to exercise payment-before-start validation.
3. In Reading Room, choose a draft report for editing and a finalized report for history/amendment testing. Enable finalized history to see all report states. Two clinical visits are available for draft creation.
4. In Inventory, inspect the received order and its batches, the placed/draft orders, the low-stock cannula and expiry values.
5. In Insurance, inspect approved/requested/denied authorizations and the different claim stages. Government approvals have a synthetic attachment supplied before the decision.
6. In Payroll and Cash, inspect the computed/approved/draft runs, payslips, recorded payments, closed session and pending handover. All amounts are fictional.

**SQL sign-in provisioning completed after the user's explicit approval for all eight demo accounts.** The normal seed command does not perform it; the approved run used the separate opt-in. The exact principals, roles and permission codes are recorded in `audit-results/demo-data-2026-10-25/sql-access-plan.json`: eight contained users in `RadiologyCenter`, each in `EGcareClient`, with the corresponding DEMO role permissions; no SQL server login, sysadmin membership or change to the original administrator.

All eight generated credentials authenticated successfully in a local shared-memory SQL check. `Identity.ReadDesktopPrincipal` confirmed the exact approved permissions, `IsAdministrator=false` and `MustChangePassword=true` for every demo account. The evidence is in `sql-account-verification.json`. These checks used the local development transport; the intended clinic server still needs its Release TCP/TLS connection configured and verified separately.

## Verification and limits

The seed tool compiled with 0 warnings and 0 errors. Its application operations verified all 29 populated lists, the calendar, Reading Room queue and six analytics endpoints. SQL checks found no orphan patients, examination types or reports; `DBCC CHECKCONSTRAINTS` reported no violations. All 7 PDF attachment contents are stored. The progress journal records 449 completed operations, including the separately approved demo SQL provisioning, and permits resuming the same run without recreating recorded data. Existing administrator state was checked after completion.

The actual Windows app was opened after seeding. The dashboard displayed 24 patients, 42 examinations, 6 inventory items and 2 in-progress examinations. Calendar equipment rows and cards loaded; appointment details showed the patient, room, duration, status and priority, and Escape dismissed the panel correctly. The Reading Room displayed populated worklist entries and opened the amended DEMO report at version 2 with its sections and findings. There are intentionally no fake image links; the image pane shows the no-images state.

This dataset enables feature testing; it does not mean every feature has now passed end-to-end testing. No PACS study was fabricated, no nonexistent image UID was attached and no external notification was delivered. Real imaging/viewing still requires the configured PACS and a test DICOM study. Two-workstation concurrency, production account permissions, exports/imports, failure recovery, installation and updates still need their own checks.
