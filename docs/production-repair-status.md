# Production repair status

Updated 9 October 2026. EGcare is one Windows desktop application on every clinic computer. Business operations run inside the app and connect directly to the same SQL Server database on the admin PC. No localhost business server, API process, IIS installation or internet connection is required for routine use. SQL Server and the central Orthanc image archive are background infrastructure on the admin PC.

The [original audit](production-readiness-review.md) records the earlier architecture and pre-repair findings. The [installation guide](lan-deployment.md) describes the approved shared-database architecture.

## Implemented

- Move all application modules and operation dispatch into the embedded `RadiologyCenter.Clinic` library. Remove the old web-server project, local-process startup, HTTP authentication middleware and SignalR client. Validate standalone development startup without HTTP routing services. Preserve private Visual Studio configuration in an ignored Debug-only settings file; exclude it from publication.
- Use an individual contained SQL user for each clinic account. Runtime accounts have neither database ownership nor user-management DDL permission. SQL policies enforce mapped account status, permissions and cash-session ownership; client JWT claims do not grant SQL authority. Only clinic administrators can create/reset accounts and change roles. Passwords remain in memory. Password resets revoke running app sessions, and deactivations revoke database permissions immediately.
- Keep encrypted SQL connections with certificate validation. The public clinic connection file contains addresses only and rejects loopback endpoints. Production sign-in opens the shared database; ordinary startup does not migrate or seed it.
- Add explicit admin maintenance: require Windows SQL administration, refuse an existing database under the new-database option, back up and verify existing databases before changes, reject backup overwrites, import legacy insurance documents while preserving originals, and install database security. Exclusive/shared SQL leases prevent upgrades while clients are connected; pooled-session locks are explicitly released. Migration and security fingerprints reject incompatible workstation versions.
- Store insurance document contents in SQL alongside their metadata and transaction. Soft deletion retains content. Persist domain-event facts inside their originating transaction, without a background event server. Snapshot examination fees synchronously during completion.
- Repair calendar submission, durations, Cairo/UTC conversion, resource selection, shift/leave validation and simultaneous booking conflicts. Keep unassigned and out-of-hours bookings accessible.
- Make payment/refund and cash-ledger changes atomic. Enforce one open cash session per user. Serialize purchase-order receipt, reject expired stock, and prevent duplicate suppliers/catalogue types.
- Validate report patient/radiologist associations, preserve finalized versions and require a revision on report mutations. Stale edits report a conflict instead of overwriting another workstation's content.
- Connect images to the central HTTPS Orthanc origin with each person's viewing credentials. Independently verify exact patient/accession/study identity before linking. Verify image-account credentials before saving them in memory; restrict credentials to the configured image origin. The supplied archive policy denies image modification by viewing accounts.
- Replace whole-history worklist downloads and individual patient queries with a server-paged SQL worklist containing patient/report summaries. Poll every 15 seconds, search on the server, retain the current report editor, and offer finalized-report history explicitly. Remove simulated series buttons; OHIF supplies the actual series.
- Produce one self-contained Windows application through Velopack. Check the clinic folder/UNC share at sign-in and expose downloads/restarts before sign-in and in the profile menu. Applying an update requires an explicit restart; drain active business operations before releasing the database maintenance lease. Do not package a separate EGcare server or development secrets. Bound diagnostic file size/retention and suppress SQL/request logging that could contain patient values.
- Require strong new passwords, preserve existing credentials during maintenance, handle permission arrays in sessions, and show recoverable configuration/sign-in errors. Keep WebView2 user data in the Windows user's local app-data folder, outside installation/release files. Unconfigured SMS/email/push delivery reports failure rather than claiming success.

## Verification

Local verification completed on 9 October 2026. **511 tests passed, zero failed, zero skipped:** 474 tests across all eleven business modules, 19 direct-database/runtime tests and 18 desktop startup/security/logging tests. The tests use uniquely named databases on the dedicated `(localdb)\EGcareIntegrationTests` instance; the configured `RadiologyCenter` database is not used by these checks. Local TRX evidence is in `audit-results/final-direct-suite`, `audit-results/direct-security.trx` and `audit-results/desktop-startup.trx` (ignored diagnostic artifacts).

The checks include direct SQL account permissions and spoofing attempts, two independent clients sharing committed records, paid examination completion, shared report conflicts, worklist pagination, account revocation, lost sessions, backup-first upgrades, repeated upgrades, backup overwrite refusal and maintenance while a client is connected. Shutdown tests prove that active operations finish before the maintenance lease is released. Development startup validates DI and runs business handlers without HTTP routing. Synthetic sensitive-value tests verify that failed business commands and exception diagnostics do not persist passwords/names. Desktop checks also cover permission arrays, malformed sessions, portable configuration, unsafe addresses, log rotation and an unavailable logging folder.

The final Windows Debug build completed with zero warnings and zero errors; its private configuration copy matches the preserved source. Release publication succeeded into `audit-results/publish/final-app` with development configuration, old server binaries and test probes excluded. A probe using the published self-contained runtime/dependency manifest started the business host, checked the schema, compiled/invoked handlers, signed in and queried only a guarded test database. The actual Windows executable passed the [versioned Velopack install-hook smoke test](https://docs.velopack.io/integrating/testing) without installing the app. The local **unsigned** Velopack 1.0.0 candidate and LAN feed are in `audit-results/release-verified`; this is a staging candidate, not a deployed or signed clinic release.

The installed Orthanc DICOMweb/OHIF plugins passed a separate HTTPS probe with a disposable synthetic archive: exact patient/accession metadata, series/instance lookup, actual frame bytes, authenticated OHIF route, anonymous denial and viewer write denial. No existing archive or scanner data was used. PowerShell scripts passed syntax checks, generated public configuration passed safe/unsafe input checks, 158 project references resolved, localization JSON parsed, and the desktop package audit reported no known vulnerable NuGet packages. Remote CI/release workflows have not been executed.

CI release publication now requires a configured signing provider and `EGCARE_SIGN_TEMPLATE`; it verifies the installer and packaged app signatures before publishing. Signing credentials were not supplied for this local candidate. Release payload checks also reject browser user data.

## Before go-live

Run the [two-workstation acceptance checks](lan-deployment.md#acceptance-before-clinical-use) on the intended LAN using synthetic data. Actual Windows UI interaction, scanner mapping, archive/viewer compatibility, certificate installation, firewall rules, clean-machine installation, clinic-sized performance and a full backup restore need verification on that environment. Passing local tests cannot establish those external conditions.

Direct SQL assumes trusted, managed clinic workstations. SQL protects permissions and accounts, but a person with allowed SQL table-write access can issue SQL outside the app and bypass some application workflow checks. This architecture does not provide the same isolation from a modified client as a service API. SQL backups and Orthanc data require access control, encryption at rest and a tested restore procedure. Image accounts are independent: revoke the matching Orthanc account when disabling a user's image access.

## Existing database recovery

The original audit/test configuration wrote to the configured `RadiologyCenter` database before isolation was repaired. Known effects include synthetic examination/catalogue/cash records and changes to the existing administrator's credentials/lockout state. The review databases are newly seeded databases, not a pre-audit backup; they cannot establish the original state.

Automatic approval review rejected the proposed deletion/reset because record names/counts did not prove ownership of all affected data and credential-reset authorization was insufficient. No automatic clinic-data cleanup or administrator reset has been applied. Review the evidence and obtain explicit approval for an exact recovery action, preferably using a verified pre-audit backup. This remains a go-live blocker if that database will be used for the clinic. New integration runs are protected against repeating the incident.
